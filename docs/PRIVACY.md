# Privacy Notice

**Project:** AuditChain  
**Status:** Prototype notice for the #AI4Elections 2026 submission  
**Last reviewed:** 2026-10-30

## Scope and intended use

AuditChain is a defensive prototype for a simulated electoral-results transmission workflow. It is intended for synthetic demonstration data only. It must not be used to submit real voter information, real polling-unit results, identity documents, or confidential election records.

## Data the prototype may process

Depending on the enabled route and configured provider, the application may process:

- Synthetic result/evidence payloads supplied to the API.
- Audit-event fields, timestamps, actor/role labels, and chain hashes.
- Evidence fingerprints and idempotency identifiers used to prevent duplicate processing.
- Human review decisions and AI-assisted review output.
- Authentication material supplied in request headers, which should be used only for authentication and must never be placed in request bodies or logs.
- Operational metadata generated by the hosting platform, such as request and error logs.

Evidence hashes are not a guarantee of anonymity: a hash can still be linkable to a known file or record. Do not upload personal or sensitive data.

## AI processing

The default vision path is a mock provider. If an HTTP vision provider is configured, the relevant evidence may be sent to that provider. Before enabling a third-party provider, the operator must review its privacy policy, retention practices, location of processing, and contractual terms. No third-party AI provider is required for the mock demonstration.

AI output is advisory. A human reviewer is responsible for review decisions; AI output must not be treated as a finding of fraud.

## Storage and retention

The current default is SQLite. On a host with ephemeral storage, records can be lost when the service restarts or redeploys. PostgreSQL is supported by the application, but an external PostgreSQL connection has not yet been configured for the deployed service. Do not assume that production-grade persistence, backups, or a defined retention schedule are in place.

Operators should use synthetic records, limit access to the service, and remove demonstration data when it is no longer needed, subject to any event/audit evidence needed for the demo.

## Sharing and disclosure

The project does not intentionally sell user-submitted data. Hosting, database, or AI providers may process data as part of their service when configured. Publicly published checkpoint anchors contain integrity metadata and should not contain evidence payloads or API secrets.

## Security responsibilities

- Never commit API keys, database credentials, signing seeds, bot tokens, or other secrets.
- Configure secrets only in the relevant hosting/provider secret store.
- Restrict API keys by role and rotate any key suspected of exposure.
- Use synthetic data only.
- Do not expose the prototype to sensitive real-world workflows.

## Requests and contact

For a privacy or security concern, open a private security advisory if GitHub enables that feature for the repository; otherwise contact the repository maintainer through the repository's GitHub page. Do not include secrets or personal data in a public issue.

## Important limitation

This notice describes the prototype as currently understood; it is not a claim of legal compliance or a substitute for a production privacy impact assessment. Before any real-world deployment, define a lawful basis, data controller/operator responsibilities, retention periods, deletion procedures, breach handling, vendor agreements, and applicable jurisdictional obligations.
